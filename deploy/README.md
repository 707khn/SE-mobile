### Что остаётся незакрытым до шага 7

Проверка доступа **выключена** (`REQUIRE_AUTH=0`). Права и пропуски
написаны и проверены, но пока не действуют: `/payslip`, `/leaves` и
остальные отвечают кому угодно, как раньше. Включать только после того,
как новая сборка дойдёт до всех — иначе у необновившихся перестанет
работать всё.

~~Пароли 23 перенесённых учёток равны табельным номерам~~ — **закрыто.**
Пароли из `app.py` убраны, а сменить свой теперь просят у всех, у кого он
всё ещё равен табельному номеру: сервер узнаёт это при входе и при первом
запуске после обновления. В `_CREDENTIALS` остались только табельные
номера — по ним восстанавливается пропавшая строка в `user_accounts`.
В истории git старые пароли есть во всех коммитах; репозиторий приватный,
публичным делать нельзя, и пароли из истории с этого момента ничего не
открывают — учётки их сменят.

**При первом запуске после обновления сервер меняет пароль учётной записи
`admin`** (он был `admin`) и печатает новый в журнал — один раз:

```bash
sudo journalctl -u se-mobile --since "10 minutes ago" | grep -i "пароль администратора"
```

Задать свой заранее — вместо случайного — можно так, до перезапуска:

```bash
echo 'ADMIN_PASSWORD=придумайте-длинный' | sudo tee -a /etc/se-mobile.env
```

Пропуски, выданные администратору раньше, гасятся: в приложении под `admin`
надо войти заново. Остальных это не касается — их пропуски действуют.

### Проверки сервера

Их гоняет сборка при каждой правке в `se-mobile-backend/` — **дважды**: на
SQLite и на настоящем PostgreSQL 16.

Второй прогон не перестраховка. SQLite прощает то, чего PostgreSQL не прощает:
длину строковых колонок он не проверяет вовсе, а внешние ключи по умолчанию не
ведёт. На обоих здесь уже обжигались на боевом сервере — на длине колонки и на
`auth_tokens` при склейке сотрудников, — и в обоих случаях проверки на SQLite
были зелёными.

Первый же прогон на PostgreSQL нашёл третий такой случай, в уборке за самой
проверкой.

У себя:

```bash
cd se-mobile-backend && pytest tests/ -q                       # SQLite
DATABASE_URL=postgresql://... pytest tests/ -q                 # PostgreSQL
```

### Уведомления

Пока Firebase не настроен, уведомления ничего не стоят: отправка возвращает
ноль и сразу. В день, когда его настроят, каждая отправка станет обращением к
Google — а звать её умеют турникет, выкладка меню, загрузка расчётных листков
и объявление.

Поэтому отправка идёт **в стороне от запроса**, через очередь и одного
работника. Хуже всего это было бы на турникете: в пересменку пятьсот проходов
за несколько минут, и каждый ждал бы Google, прежде чем СКУД получит ответ.

Работник один, а не поток на событие: пятьсот проходов — это пятьсот потоков.
Очередь ограничена тысячей; переполнилась — уведомление теряется с записью в
журнал. Пропуск человека важнее сообщения о нём.

### Сторож

Сбой 12 сентября прожил **восемь дней**: приложение отвечало, база лежала,
systemd считал службу исправной, и узнали обо всём от сотрудника.

Теперь `/health` спрашивает базу запросом, а не «открыт ли порт», и отвечает
503, когда она не отвечает. Сторож (`se-mobile-watchdog.timer`, раз в две
минуты) при **двух неудачах подряд** поднимает то, что упало: сначала
PostgreSQL, если лежит он, потом приложение. Чаще раза в пятнадцать минут не
перезапускает — сторож, дёргающий службу каждые две минуты, вредит больше
самого сбоя.

Всё, что он делал, лежит в `/var/lib/se-mobile/watchdog/outages.log`, а
последние записи видны в приложении: «Обновление» → «Перебои сервера».

```bash
curl -s https://api.se-btrz.com/health
systemctl status se-mobile-watchdog.timer
sudo tail -20 /var/lib/se-mobile/watchdog/outages.log
```

**Чего сторож не умеет.** Если машина выключится целиком, никто никому не
напишет: он живёт на ней же. Для этого — проверка снаружи, ниже.

### Проверка снаружи

Раз в час GitHub (workflow «Сервер доступен снаружи», `.github/workflows/uptime.yml`)
делает то же, что телефон: запрос из интернета к `https://api.se-btrz.com/health`.
Три попытки с паузой; не ответил — запуск красный. Заодно смотрит срок
сертификата и краснеет, если осталось меньше двух недель: certbot продлевает
сам, но продление ломается молча.

Красный запуск — это письмо от GitHub, **если письма включены**: github.com →
Settings → Notifications → **Actions** → отметить «Email» и «Only notify for
failed workflows». Письмо уходит тому, кто последним менял расписание в этом
файле, — то есть тому, кто слил PR с ним.

Проверить вручную: Actions → «Сервер доступен снаружи» → **Run workflow**.

Стоит около 720 минут Actions в месяц из 2000 бесплатных для закрытого
репозитория: каждый запуск округляется до минуты.

### Раздать новую сборку

Здесь — раздача файлом с нашего сервера. Публикация в Google Play — отдельно:
`deploy/google-play/README.md`.

Приложение ставится руками, и пока скачивать его было неоткуда, обновлялись
единицы — а без этого нельзя включить `REQUIRE_AUTH=1`: у необновившихся всё
перестанет работать.

Теперь сборка лежит на сервере, а приложение само говорит человеку, что вышла
новая, и открывает ссылку на скачивание.

#### Сборка приезжает на сервер сама

После каждого слияния в `main` GitHub собирает APK и выкладывает его в
**Releases**. Сервер раз в десять минут спрашивает GitHub, нет ли сборки новее,
скачивает её, сверяет размер и контрольную сумму и кладёт в
`/var/www/se-mobile` — оттуда её и предлагают телефонам. Делает это
`deploy/fetch-apk.sh` по таймеру `se-mobile-fetch-apk.timer`.

Раньше файл переносили руками — Releases → компьютер → `scp` → `mv`, — и
шаг то забывали, то `scp` обрывался на середине: сборка 1.16.17 лежала в
Releases, а телефонам сервер предлагал 1.15.2.

**Настроить один раз.**

1. **Токен GitHub только на чтение.** github.com → аватар → **Settings** →
   **Developer settings** → **Personal access tokens** → **Fine-grained
   tokens** → **Generate new token**:
   - *Token name*: `se-mobile server releases`;
   - *Expiration*: самый долгий, какой дают, — и поставьте себе напоминание
     за неделю до конца;
   - *Repository access*: **Only select repositories** → `707khn/SE-mobile`;
   - *Permissions* → *Repository permissions* → **Contents: Read-only**
     (Metadata добавится сам). Больше ничего не нужно.

   **Generate token** и скопируйте его — второй раз GitHub его не покажет.
2. **На сервере:**

   ```bash
   cd /opt/se-mobile && sudo git pull
   sudo bash deploy/install-fetch-apk.sh
   sudo nano /etc/se-mobile-fetch-apk.env     # GITHUB_TOKEN=github_pat_…
   sudo systemctl start se-mobile-fetch-apk
   journalctl -u se-mobile-fetch-apk -n 5 -o cat
   ```

   В журнале — «Забираю se-mobile-…apk» и «Готово», или ничего, если новее
   того, что уже лежит, сборки нет. Файл с токеном читает только root.

**Каждый день** делать ничего не нужно. Если сборки перестали приезжать —
истёк токен, таймер не запускается, кончилось место, — причина видна в
приложении на экране **«Обновление»**, под сборкой на сервере. Там же за две
недели до конца срока появится предупреждение о токене. Подробности — в
журнале: `journalctl -u se-mobile-fetch-apk --since today -o cat`. Если там «GitHub не
принял токен» — срок токена кончился: заведите новый (пункт 1) и впишите в
`/etc/se-mobile-fetch-apk.env`.

**Откатить плохую сборку** — удалить её файл:

```bash
sudo rm /var/www/se-mobile/se-mobile-1.20.0+60.apk
```

Обратно таймер её не принесёт: он берёт только сборки новее всех, что уже
забирал. Следующая сборка приедет как обычно. Хранятся три последние —
предыдущие есть куда вернуть.

**Руками, если таймер не настроен или GitHub недоступен.** Releases →
скачать `se-mobile-<версия>+<номер>.apk` → на сервер:

```powershell
scp "se-mobile-1.16.17+50.apk" ubuntu@87.199.130.179:/tmp/
```

```bash
sudo mv /tmp/se-mobile-*.apk /var/www/se-mobile/
sudo chmod 644 /var/www/se-mobile/se-mobile-*.apk
curl -s --resolve api.se-btrz.com:443:127.0.0.1 https://api.se-btrz.com/api/app/latest
```

В ответе — версия и номер сборки только что положенного файла.

Имя файла менять не надо: **версия записана в имени**, сборка сама его так
называет, и сервер читает версию оттуда же. Отдельного файла с номером версии
нет намеренно — номер, который надо где-то повторить, рано или поздно отстаёт.

Сборок может лежать несколько; предлагается та, у которой **больше номер
сборки** (число после `+`). Именно его смотрит Android, решая, ставить ли
поверх установленного, — 1.9.0+9 поверх 1.8.2+12 не встанет.

Лежит ли сборка на сервере, видно в приложении: «Обновление» → «Сборка на
сервере».

### Часы: сервер по UTC, предприятие по UTC+5

Сервер стоит в Астане и живёт по UTC — менять это не нужно, и не надо. Но в
базе лежат часы двух родов, и путать их нельзя:

| Что | Чьё время |
|---|---|
| Проходы из СКУД, периоды расчётных листков | **местное**, как в выгрузке |
| Сроки пропусков, время новостей, отметки сидеров | **UTC**, как `datetime.utcnow()` |

Встречались они там, где сервер спрашивал «какое сегодня число» про местные
данные. С полуночи до пяти утра его «сегодня» — это вчера у проходной: меню
столовой в эти часы показывалось вчерашнее, табель за «сегодня» — за вчера.
Теперь такие места берут дату через `_plant_today()`.

Если предприятие когда-нибудь окажется в другом поясе, менять одну строку —
`_PLANT_TZ` в `app.py`.

### Если будут выгрузки в Excel

Замеры на 500 000 строк (проходы турникета за год, 500 сотрудников):

| Режим записи openpyxl | Время | Память |
|---|---|---|
| обычный | 49,6 с | **1167 МБ** |
| `Workbook(write_only=True)` | 38,5 с | **38 МБ** |

Писать **только потоком**. В обычном режиме одна выгрузка съедает больше
памяти, чем есть на машине, и система убивает процесс. Выгрузку проходов
делить по месяцам: 40 000 строк вместо 500 000, три секунды вместо сорока.

## Шаг 1. Войти и закрыть парольный вход

Сервер выдаётся с паролем в письме. Пароль к SSH подбирают боты
круглосуточно, поэтому первым делом — ключ, и пароль выключить.

```powershell
ssh -l ubuntu 87.199.130.179
```

Форма `-l ubuntu` вместо `ubuntu@` — потому что символ `@` теряется при
вставке в некоторых терминалах Windows. По той же причине ниже везде
полные пути вместо `~`.

Положить свой ключ (на сервере, по одной команде):

```bash
mkdir -p /home/ubuntu/.ssh
chmod 700 /home/ubuntu/.ssh
nano /home/ubuntu/.ssh/authorized_keys
chmod 600 /home/ubuntu/.ssh/authorized_keys
```

В `nano` вставить содержимое `id_ed25519.pub` со своего компьютера
(в PowerShell: `Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard`),
сохранить Ctrl+O, Enter, Ctrl+X.

Проверить вход по ключу **из нового окна**, не закрывая текущее. Когда
зашло без пароля:

```bash
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo systemctl restart ssh
```

**Если пишет `Permission denied (publickey)`** — ключ не подошёл. Проверьте,
что в PS Cloud загружена именно публичная часть:

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub
```

**Если висит без ответа** — сервер ещё не запустился (первый старт занимает
пару минут) или в группе безопасности закрыт порт 22.

## Шаг 2. Дать серверу доступ к репозиторию

Репозиторий приватный, поэтому сервер не может просто так скачать код.
Нужен **ключ развёртывания** — отдельный ключ только на чтение и только
для этого репозитория.

На сервере:

```bash
sudo apt-get update && sudo apt-get install -y git
sudo mkdir -p /root/.ssh && sudo chmod 700 /root/.ssh
sudo ssh-keygen -t ed25519 -N "" -C "se-mobile-server" -f /root/.ssh/id_ed25519
sudo cat /root/.ssh/id_ed25519.pub
```

Последняя команда выведет одну строку `ssh-ed25519 AAAA… se-mobile-server`.
Скопируйте её и добавьте в GitHub:

> репозиторий **SE-mobile** → **Settings** → **Deploy keys** →
> **Add deploy key** → вставить строку → **Add key**

Галочку **«Allow write access» не ставьте**: серверу нужно только читать.
Если ключ утечёт, писать в репозиторий им будет нельзя.

## Шаг 3. Настроить сервер

Теперь код скачается:

```bash
sudo git -c core.sshCommand="ssh -l git" clone --depth 1 ssh://github.com/707khn/SE-mobile.git /tmp/se-mobile
sudo bash /tmp/se-mobile/deploy/setup.sh
```

Адрес записан как `ssh://github.com/...` вместо `git@github.com:...` по той
же причине — чтобы не потерялась «собачка».

При первом подключении git спросит про доверие к `github.com` — ответьте
`yes`.

Займёт 5–10 минут. Скрипт ставит и настраивает:

| Что | Зачем |
|---|---|
| Файл подкачки 2 ГБ | На машине 2 ГБ памяти; не даёт системе убить PostgreSQL при всплеске |
| PostgreSQL | База; пароль генерируется сам и лежит в `/etc/se-mobile-db-password` |
| Python + gunicorn | Приложение, три процесса |
| nginx | Принимает запросы снаружи и передаёт приложению |
| systemd | Автозапуск при перезагрузке и перезапуск при падении |
| Суточные копии | `pg_dump` в 03:30, хранятся 30 дней в `/var/backups/se-mobile` |
| ufw | Открыты только 22, 80 и 443 |

Повторный запуск скрипта безопасен: сделанное пропускается, файл
`/etc/se-mobile.env` не перезаписывается.

Проверка, что приложение отвечает:

```bash
curl -s http://localhost/ | head -c 200
```

Должно вернуть `{"status": "ok", "service": "SE-mobile API", ...}`.

## Шаг 4. Прописать имя в DNS

**Это делаете вы, у регистратора домена `se-btrz.com`.** Сертификат
выдаётся на имя, а не на адрес, поэтому без этой записи HTTPS не включить.

Добавьте запись:

```
api.se-btrz.com.   A   87.199.130.179
```

Разойдётся обычно за 10–30 минут, иногда до суток. Проверить с сервера:

```bash
dig +short api.se-btrz.com
```

Когда команда покажет `87.199.130.179` — переходите дальше.

### И то же самое во внутренней зоне

**Одной записи у регистратора мало.** Внутри предприятия зону `se-btrz.com`
держит свой DNS — `ODIN` на `192.168.1.10`, — и рабочие компьютеры спрашивают
его. Для своей зоны он считает себя единственным источником и наружу за ней
не пойдёт: чего у него нет, того для них не существует.

Телефоны в мобильном интернете этого не замечают, а в заводском Wi‑Fi
упираются так же — «Ошибка подключения к серверу». А программа
загрузки меню на компьютере с 1С упёрлась ровно в это: «Невозможно разрешить
удаленное имя».

Поэтому ту же запись нужно завести и на `ODIN`. Проще всего зайти на сам
сервер через удалённый рабочий стол — «Диспетчер DNS» там уже стоит:

**Диспетчер DNS** → `ODIN` → **Зоны прямого просмотра** → `se-btrz.com` →
правой кнопкой → **Создать узел (A или AAAA)**, имя `api`, адрес
`87.199.130.179`.

То же самое командой, в PowerShell на сервере:

```powershell
Add-DnsServerResourceRecordA -ZoneName "se-btrz.com" -Name "api" `
    -IPv4Address "87.199.130.179"
```

Менять зону может не всякая учётная запись: нужны права администратора
домена либо делегированные на зону. Нет прав — задача для тех, кто ведёт
сеть, и формулируется одной строкой.

Проверка с любого рабочего компьютера — оба ответа должны совпасть:

```powershell
nslookup api.se-btrz.com
nslookup api.se-btrz.com 8.8.8.8
```

## Шаг 5. Получить сертификат

```bash
sudo certbot --nginx -d api.se-btrz.com --agree-tos -m ваша@почта --redirect
```

Certbot сам допишет настройки в nginx и включит перенаправление с
`http://` на `https://`. Продлевается автоматически, вмешательства не

Проверка снаружи, из PowerShell:

```powershell
curl.exe https://api.se-btrz.com/
```

## Шаг 6. Перенести данные с Render

На старом сервере (Render) снимите копию базы и перенесите её сюда.
Строку подключения возьмите в панели Render → база → *External Database URL*.

С компьютера с Windows, если установлен PostgreSQL-клиент:

```powershell
pg_dump "СТРОКА_ПОДКЛЮЧЕНИЯ_RENDER" > render.sql
scp render.sql ubuntu@87.199.130.179:/tmp/
```

Затем на сервере. **База пересоздаётся перед восстановлением** — сидеры уже
наполнили её при первом запуске, и дамп поверх этого не ляжет: посыплются
ошибки «таблица уже существует» и «дубль первичного ключа».

```bash
sudo systemctl stop se-mobile
sudo -u postgres dropdb se_mobile
sudo -u postgres createdb -O se_mobile se_mobile
sudo -u postgres psql se_mobile < /tmp/render.sql
sudo systemctl start se-mobile
```

Сидеры после восстановления повторно не отработают: журнал `applied_seeds`
приезжает вместе с дампом, и они увидят себя уже применёнными.

Сверить, что всё доехало:

```bash
sudo -u postgres psql se_mobile -c "
  SELECT 'сотрудники' AS таблица, count(*) FROM employees
  UNION ALL SELECT 'листки', count(*) FROM payslips
  UNION ALL SELECT 'проходы', count(*) FROM access_records
  UNION ALL SELECT 'учётные записи', count(*) FROM user_accounts;"
```

Числа должны совпасть с тем, что показывает Render.

## Шаг 7. Переключить приложение

В `lib/utils/variables.dart` поменять адрес:

```dart
static const String baseUrl = 'https://api.se-btrz.com';
```

Не забыть про два места, которые ходят на сервер помимо приложения:

- **система турникета** — она шлёт события на `/api/turnstile`; новый

## Шаг 8. Включить проверку доступа

Пока в `/etc/se-mobile.env` стоит `REQUIRE_AUTH=0`, сервер принимает запросы
без пропуска — иначе старые сборки приложения отвалились бы разом.

Посмотреть, остались ли такие запросы:

```bash
sudo journalctl -u se-mobile --since "24 hours ago" | grep -c "Unauthenticated request"
```

Когда счётчик станет нулевым несколько дней подряд — значит все обновились:

```bash
sudo sed -i 's/REQUIRE_AUTH=0/REQUIRE_AUTH=1/' /etc/se-mobile.env
sudo systemctl restart se-mobile
```

С этого момента расчётные листки и всё остальное закрыты для всех, кроме
владельца, его начальника и администратора.

## Повседневное

| Задача | Команда |
|---|---|
| Обновить приложение | `cd /opt/se-mobile && sudo git pull && sudo systemctl restart se-mobile` |
| Посмотреть логи | `sudo journalctl -u se-mobile -f` |
| Состояние служб | `systemctl status se-mobile nginx postgresql` |
| Снять копию сейчас | `sudo systemctl start se-mobile-backup` |
| Список копий | `ls -lh /var/backups/se-mobile` |
| Восстановить из копии | см. ниже — копии зашифрованы |

**Восстановление стоит отрепетировать заранее**, а не в тот день, когда оно
понадобится: копия, которую ни разу не разворачивали, — это надежда, а не
резерв.

### Копии не делались три недели

При установке папку `/var/backups/se-mobile` никто не создавал, а копирование
идёт от пользователя `postgres`, которому в `/var/backups` писать нельзя.
Служба падала на первой же строке — `mkdir: Permission denied` — каждую ночь,
и обнаружилось это случайно, три недели спустя. В `setup.sh` папка теперь
создаётся; на сервере, поставленном раньше, один раз вручную:

```bash
sudo mkdir -p /var/backups/se-mobile
sudo chown postgres:semobile /var/backups/se-mobile
sudo chmod 750 /var/backups/se-mobile
sudo systemctl start se-mobile-backup
```

Проверять, что копии идут, теперь можно не заходя на сервер: дата последней
видна в админ-панели, на экране «Обновление». А на сервере — так:

```bash
systemctl list-timers se-mobile-backup     # когда сработает в следующий раз
systemctl status se-mobile-backup          # чем кончился прошлый запуск
```

### Копии зашифрованы

В копии зарплаты, ИИН и телефоны всего предприятия. Лежит она файлом на том
же диске, где и база, поэтому шифруется ключом `/etc/se-mobile-backup-key`.

Восстановление:

```bash
sudo systemctl stop se-mobile
sudo openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
     -pass file:/etc/se-mobile-backup-key \
     -in /var/backups/se-mobile/ФАЙЛ.sql.gz.enc \
  | zcat | sudo -u postgres psql se_mobile
sudo systemctl start se-mobile
```

**Ключ заберите с сервера и храните отдельно** — там же, где ключ подписи
приложения:

```powershell
scp -o User=ubuntu 87.199.130.179:/tmp/backup-key .
```

(сначала на сервере: `sudo cp /etc/se-mobile-backup-key /tmp/backup-key &&
sudo chmod 644 /tmp/backup-key`, а после копирования — `rm /tmp/backup-key`.)

Скажем честно, чего это шифрование **не** даёт: оно защищает унесённый файл
копии, но не спасает от того, кто получил сервер целиком — ключ лежит рядом.
Настоящая защита — забирать копии с сервера. Раз в неделю с домашнего
ноутбука:

```powershell
scp -o User=ubuntu "87.199.130.179:/var/backups/se-mobile/se_mobile_*.sql.gz.enc" .
```

Копия, которая лежит только на сервере, не переживёт потерю сервера.

## Если приложение отвечает «ошибка сервера (503)»

503 при входе означает одно: приложение не смогло обратиться к базе. Сначала
смотрим, жива ли она:

```
systemctl status postgresql@16-main --no-pager -l | head -25
```

**Случай из жизни.** 12 сентября 2026 база не поднялась после перезапуска:

```
could not translate host name "localhost", service "5432" to address:
    Temporary failure in name resolution
WARNING: could not create listen socket for "localhost"
FATAL:  could not create any TCP/IP sockets
```

PostgreSQL слушал `localhost` — то есть при запуске просил систему перевести
имя в адрес, а в тот момент перевести его не удалось. Служба сдалась с первой
попытки и молча пролежала **неделю**: узнали об этом от сотрудника, который
не смог войти.

Лечится тем, что имя больше не участвует:

```
sudo sed -i "s/^#\?listen_addresses\s*=.*/listen_addresses = '127.0.0.1'/" \
    /etc/postgresql/16/main/postgresql.conf
sudo systemctl restart postgresql@16-main
```

и в `/etc/se-mobile.env` в `DATABASE_URL` вместо `@localhost/` — `@127.0.0.1/`,
после чего `sudo systemctl restart se-mobile`. В `deploy/setup.sh` то и другое
уже так, эта правка нужна только серверам, поставленным раньше.

Плюс служба базы теперь пробует запуститься снова, а не сдаётся с первого
раза (`Restart=on-failure` в `/etc/systemd/system/postgresql@16-main.service.d/`).

**Неделя простоя — это про отсутствие присмотра, а не про базу.** Пока никто
не следит за сервером, любая такая поломка будет жить до первой жалобы.

## Если телефоны пишут «Ошибка подключения к серверу», а сервер жив

Так бывает, когда приложение отвечает (`curl -s http://127.0.0.1:8000/health`
→ `ok`), а до него не доходят. С версии 1.14.1 под сообщением на телефоне есть
мелкая строка с причиной — по ней видно, какой из случаев ниже.

**1. Пропал HTTPS в nginx** (на телефоне `Connection refused` или
`HandshakeException`). Файл `deploy/nginx-se-mobile.conf` — без секции 443:
её дописывает certbot на сервере. Скопировали файл из репозитория поверх
рабочего — секция пропала. Проверка на сервере, в обход внешнего адреса:

```bash
curl -sSI --resolve api.se-btrz.com:443:127.0.0.1 https://api.se-btrz.com/health
sudo grep -n "listen\|ssl_certificate" /etc/nginx/sites-enabled/se-mobile
```

Нет строки `listen 443` — вернуть сертификат в конфиг (сам сертификат цел,
заново его выпускать не нужно):

```bash
sudo certbot install --nginx --cert-name api.se-btrz.com --redirect
sudo nginx -t && sudo systemctl reload nginx
```

`setup.sh` теперь делает это сам после копирования конфига, а сторож
записывает в журнал перебоев, если HTTPS перестал отвечать при живом
приложении. Правьте рабочий файл на месте, а не копируйте его заново.

**2. Имя не находится во внутренней сети** (на телефоне `Failed host
lookup`). В заводском Wi‑Fi имена отдаёт `ODIN`, и записи `api` в нём может
не быть (см. шаг 4, «И то же самое во внутренней зоне»). Признак: в
мобильном интернете вход работает, в Wi‑Fi — нет. Проверка с рабочего
компьютера: `nslookup api.se-btrz.com` должен ответить `87.199.130.179`.

Проверка `curl https://api.se-btrz.com/...` с самого сервера по внешнему
имени ничего не доказывает: облако часто не пропускает запрос машины к самой
себе по внешнему адресу, даже когда снаружи всё работает. Поэтому выше —
`--resolve` на 127.0.0.1.

## Новости с сайта

Раздел «Новости» в приложении показывает два потока: объявления, которые
одобрил администратор, и материалы с сайта предприятия.

Сайт сервер обходит сам, лениво — при первом за четверть часа обращении
приложения к ленте. Порядок такой:

1. берёт адрес из `NEWS_FEED_URL`, а если строки нет — `https://se-btrz.com/news/`
   (он записан в коде, поэтому новости идут и без настройки);
2. если по адресу лента RSS или Atom — разбирает её;
3. если страница — спрашивает у самой страницы, где её лента
   (`<link rel="alternate">`), и пробует обычные адреса: `feed/`, `rss/`,
   `rss.xml`;
4. если ленты у сайта нет — разбирает саму страницу списка.

Четвёртый способ — запасной и хрупкий: он держится на вёрстке, и после
обновления сайта новости могут перестать приходить. **Если в системе
управления сайтом можно включить RSS — включите**, и укажите её адрес в
`NEWS_FEED_URL`. Найденный адрес ленты сервер запоминает и потом ходит
сразу туда.

Проверить, чем всё кончилось, можно из-под учётной записи администратора:

```
GET  https://api.se-btrz.com/api/admin/news/refresh    что было в прошлый раз
POST https://api.se-btrz.com/api/admin/news/refresh    сходить прямо сейчас
```

Ответ говорит, по какому адресу ходили, лентой взяли или страницей, сколько
новостей нашли и добавили, и что за ошибка была, если новостей нет.
